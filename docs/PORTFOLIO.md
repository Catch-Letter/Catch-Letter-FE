# CatchLetter — 문제 정의와 결정의 기록

> 이 문서는 기능 목록이 아니라, 이 프로젝트에서 **무엇을 고민했고, 어떤 가설이 틀렸고, 왜 지금의 모양이 되었는지**의 기록이다.
> 5인 팀(FE 3 · BE 1 · 디자인 1) 프로젝트라서 **내 커밋으로 확인되는 내 몫만** 내 것으로 쓴다. 내 영역은 **정답 시도(tryAnswer)/정답 확인(checkAnswer) 플로우 전반과 분리 입력(separated input) 컴포넌트** (2025-01 ~ 2025-05). 기능과 스택은 [README](../README.md).

---

## 1. 어떤 문제를 다르게 봤나

CatchLetter는 그림의 정답을 맞혀야만 편지를 읽을 수 있는 익명 우체통이다 — 메시지 전달을 작은 게임으로 만든 제품. 나는 그 게임의 핵심 고리인 **"틀리는 경험"의 설계**를 맡았다.

- **페널티는 필요하지만, 이탈의 이유가 되면 안 된다.** 무한정 시도할 수 있으면 정답 맞히기는 게임이 아니라 단순 반복이 된다 — 그래서 3번 틀리면 3분 잠금이라는 페널티를 뒀다. 대신 그 시간의 끝에 **힌트 한 글자가 도착**하게 해서, 기다림에 다시 도전할 이유를 붙였다. 페널티가 이탈 대신 재시도로 이어진다는 가설 — 이탈/재시도율 데이터로 검증하지는 못했다(§5).
- **비밀 편지는 네트워크 탭에서도 비밀이어야 한다.** 정답을 맞히기 전에 편지 내용이 클라이언트로 오면, UI로는 잠겨 있어도 개발자도구로 뜯어볼 수 있다. 편지 데이터 요청 자체를 정답 이후로 잠갔다(§4).

## 2. 가설은 어떻게 바뀌었나

### 힌트 화면의 인풋: 일반 인풋으로 교체 → 다음 날 되돌림 (2025-04-07~08, #155)
힌트를 보여줄 자리에 처음엔 정답 입력용 분리 입력 인풋(글자 단위로 칸이 나뉜 OTP식 인풋)을 그대로 썼다가, 일반 인풋으로 교체했다. 그런데 다음 날 다시 분리 입력 인풋으로 되돌리고 **disabled 처리**로 정리했다 — 힌트와 정답 입력이 다른 생김새면 화면의 연속성이 깨지고, 같은 생김새면 "여기 입력하는 건가?"가 헷갈린다. 결론은 "**모양은 유지하되 입력만 막는다**"였다. 하루 만에 오간 결정이지만 커밋에 그대로 남아 있다.

### 힌트 정책: "틀리면 타이머" → "힌트 보유 중엔 입력 자체를 잠금" (2025-04-10, #172)
처음 설계는 단순했다 — 3번 틀리면 타이머가 돌고 힌트가 열린다. 만들고 보니 힌트를 이미 받은 재도전 상태의 흐름이 어색해서, **힌트가 있으면 진입 즉시 힌트를 보여주고 타이머 동안은 정답 입력 자체를 잠그는** 쪽으로 규칙을 다시 세웠다. 상태(첫 시도/재시도/힌트 보유)마다 화면이 무엇을 보여줘야 하는지를 정의하고 나서야 플로우가 잡혔다.

### 같은 날 버린 해결책 (2025-04-10, #172)
separatedInput 관련 버그를 한 가지 방법으로 고쳤다가, **같은 날 그 해법을 버리고** `useEffect` 의존성에 `value`를 추가하는 것으로 다시 고쳤다(328f796). 증상을 덮는 수정과 원인(의존성 누락으로 value 변화에 반응하지 못함)을 고치는 수정은 다르다 — 첫 수정이 동작해도 원인이 남아 있으면 결국 돌아오게 된다.

### fetch 직접 호출 → TanStack Query로 통일 (2025-03-28, #110)
tryAnswer의 데이터 요청을 fetch로 직접 처리하다가 TanStack Query로 옮겼다. 단순 교체가 아니라 이후의 캐싱(§4)·조건부 페칭(§4)·retry 정책(§4)이 전부 이 전환 위에서 가능해졌다.

## 3. UX에서 무엇을 고민했나

### 카드는 닫힌 채로 시작해야 한다 (2025-04-02, #124)
정답 페이지에 진입하자마자 카드가 한 번 뒤집히며 시작하는 현상이 있었다 — 첫인상이 "닫힌 편지"가 아니라 "덜컹거리는 카드"였다. 진입 시엔 닫힌 상태로 고정하고, **정답을 맞힌 순간에만 카드가 자동으로 돌아가며 편지가 열리게** 했다. 맞힌 순간의 보상을 클릭 한 번 뒤로 미루지 않는 것. 로딩도 그림/편지 데이터가 **둘 다** 없을 때만 스켈레톤을 띄워 덜그럭거림을 줄였다.

### 분리 입력 인풋의 디테일 (2025-01-22 #18 ~ 2025-04-14 #191)
글자 수만큼 칸이 나뉜 OTP식 분리 입력 인풋을 라이브러리 없이 직접 만들었다 — 입력하면 다음 칸으로, 백스페이스면 이전 칸으로 포커스 이동. 여기서 오래 붙잡은 건 **한글**이었다: 조합(IME) 중인 글자는 keydown과 value가 어긋나서 조합 처리를 따로 해야 했고(#18), 출시 후에도 백스페이스를 두 번 눌러야 지워지는 불편이 발견돼 고쳤다(#191). 정답칸이 모두 채워져야 확인 버튼이 활성화되게 해서(#133) "덜 입력하고 눌러서 틀림"을 차단했다.

### 벌칙은 새로고침으로 피할 수 없어야 한다 (2025-03-20 ~ 04-07)
남은 기회 표시가 페이지를 갔다 와도 유지되게 하고(#49), 3분 타이머는 편지를 나갔다 재접근해도 이어지게 했다(#155). 게임 규칙이 클라이언트 상태에만 있으면 새로고침이 치트키가 된다 — 진입 시 서버에서 시도 상태를 조회해 그리는 구조로 만들었다.

### 그 외
- 흰색으로 그린 그림이 배경에 묻혀 안 보이는 문제 → 시도/확인 화면의 배경색 조정(2025-04-18)
- 정답 확인 화면의 한영 변환(i18n) 적용과 번역 정리(#108~#114)

## 4. 기술적으로 막혔던 지점들

### 편지 내용이 정답 전에 새고 있었다 (2025-04-11, #181)
정답 여부와 관계없이 편지 데이터가 미리 호출되고 있었다 — 비밀 편지인데 네트워크 응답에는 이미 내용이 와 있는 것. TanStack Query의 `enabled: isCorrect`로 **쿼리 실행 자체를 정답 이후로 잠갔다** (`src/hooks/useTryAnswer.ts`에 남아 있다). "UI에서 안 보여준다"와 "클라이언트에 아예 안 보낸다"는 보안상 완전히 다른 층위라는 걸 몸으로 확인한 지점.

### 타이머가 1초마다 화면 전체를 리렌더링했다 (2025-04-24, #214)
3분 타이머 상태가 페이지 훅(useTryAnswer)에 있어서, 초가 줄 때마다 페이지 전체가 다시 그려졌다. 타이머를 TryCounter 컴포넌트로 격리해 **타이머 부분만 리렌더링**되게 리팩토링했다. 자주 바뀌는 상태는 그것을 소비하는 최소 범위에 둬야 한다 — 출시 후에 돌아와서 고친 기록이다.

### 불변 데이터를 매번 다시 받고 있었다 (2025-04-05, #142)
그림·정답·편지 데이터는 한 번 만들어지면 바뀌지 않는데 화면 전환마다 refetch되고 있었다. 정적 데이터로 판단해 `staleTime: Infinity` + `gcTime` 30분을 적용해 중복 요청을 제거했다(당시 팀 측정 기준 중복 API 요청 약 66% 감소).

### 실패에도 등급이 있다 (2025-04-09, #171)
잘못된 id로 접근하면 404/403/422가 각각 다른 의미인데 처리가 없었다 — 각 상태별 에러 페이지 이동을 붙이고, retry 정책도 나눴다(재시도가 의미 있는 경우만 1회, 나머지는 기본 3회). 실패를 한 덩어리로 다루면 사용자에겐 무한 스피너, 서버엔 무의미한 재시도가 간다.

## 5. 아직 못 푼 것들

- **힌트 정책(3회 → 3분 잠금 + 힌트)의 근거가 데이터가 아니라 합의다.** 이탈률/재시도율로 검증하지 못했다. GA 계측은 이후 팀원(Sumin)이 구축했고, 내 플로우에 이벤트를 붙여 검증하는 사이클까지는 못 갔다.
- **한글 IME 대응이 완결이라고 말하기 어렵다.** 조합 처리(#18) 이후에도 백스페이스 이슈가 4월에 다시 나왔다(#191) — 분리 인풋과 한글 조합의 조합은 엣지가 계속 나오는 영역이라, 다시 만든다면 조합 상태를 명시적인 상태 머신으로 다루는 것부터 시작할 것이다.
- **팀 성과와 내 몫의 경계.** 사용자 100→500명 성장, SEO 구글 상단 노출, GA 트래킹은 팀의 성과이고 그중 GA·SEO는 팀원 커밋이다. 내 몫은 정답 플로우·분리 인풋·쿼리 계층까지 — 경계를 흐리지 않고 기록한다.
